You are halfway through a complex refactor on `feature/authentication`. Your local dev server is running, your debugger is paused at a breakpoint, and you have twelve modified files unstaged.

# The Worktree Mental Model: Branches vs. Worktrees vs. Folders

Before choosing a directory layout, developers must understand how Git distinguishes branches, worktrees, and physical filesystem directories.

<div class="overflow-x-auto my-6">
<table>
  <thead>
    <tr>
      <th>Concept</th>
      <th>What It Is</th>
      <th>Where It Lives</th>
      <th>Key Responsibility</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td><strong>Git Branch</strong></td>
      <td>Lightweight pointer to a commit hash (41 bytes)</td>
      <td><code>.git/refs/heads/&lt;branch&gt;</code></td>
      <td>Tracks the commit history and lineage.</td>
    </tr>
    <tr>
      <td><strong>Git Worktree</strong></td>
      <td>Administrative binding between a branch &amp; a directory</td>
      <td><code>.git/worktrees/&lt;name&gt;/</code></td>
      <td>Manages separate <code>index</code>, <code>HEAD</code>, and staging metadata.</td>
    </tr>
    <tr>
      <td><strong>Physical Folder</strong></td>
      <td>Actual OS filesystem directory on disk</td>
      <td>Your local drive (e.g., <code>~/projects/my-app-auth</code>)</td>
      <td>Holds source files, <code>node_modules</code>, build artifacts, and <code>.env</code> files.</td>
    </tr>
  </tbody>
</table>
</div>

When you initialize a repository, Git creates the **main working tree** where `.git` is a physical directory containing the entire object database (commits, trees, blobs, and tags).

When you create a **linked working tree** using `git worktree add`, Git does *not* duplicate the object database. Instead:

1. It creates the destination directory on disk.
2. It generates a small `.git` *file* inside that directory pointing back to the main repository:
   ```bash
   gitdir: /path/to/main-repo/.git/worktrees/<worktree-name>
   ```
3. Inside the main repository's `.git/worktrees/<worktree-name>/` directory, Git stores a private `HEAD`, a private staging `index`, and checkout configuration for that specific worktree.

Because every worktree shares the same commit graph and packfiles, commits made in any worktree are immediately accessible in every other worktree without pulling from a remote.

# 8 Proven Git Worktree Organization Strategies

Every team and individual developer has different constraints: number of repositories, Git branching models, ticket tracking requirements, and whether autonomous AI coding agents are involved.

Here are the 8 field-tested strategies for organizing Git worktrees.

![Git worktree structural topologies compared: sibling, repo-centric, and branch-type](/images/blog/how-to-organize-git-worktrees/strategy-comparison.svg)

*Three primary worktree structural topologies: Sibling layout, Repository-centric layout, and Branch-type classification.*

## Strategy 1: Sibling Folder Organization

The **Sibling Folder** layout places every worktree directory alongside the main repository in the same parent development folder.

### Filesystem Structure

```text
projects/
├── my-app/                 # Main working tree (contains .git/ folder)
├── my-app-feature-auth/    # Linked worktree -> branch: feature/auth
├── my-app-bugfix-payment/  # Linked worktree -> branch: bugfix/payment
└── my-app-experiment/      # Linked worktree -> branch: exp/wasm-test
```

### Valid Git CLI Example

Run these commands from inside your primary repository (`projects/my-app`):

```bash
# Add a sibling worktree for a new feature branch
git worktree add ../my-app-feature-auth -b feature/auth

# Add a sibling worktree for an urgent fix based on production main
git worktree add ../my-app-bugfix-payment -b bugfix/payment main

# Verify the active worktrees
git worktree list
```

### Trade-offs

- **Advantages:**
  - Extremely simple relative CLI paths (`../my-app-<name>`).
  - No risk of accidentally nesting a worktree inside an untracked subdirectory of the main repository.
  - Editors and IDE file pickers display each directory as a distinct top-level project.
- **Disadvantages:**
  - Clutters your primary `projects/` directory when you maintain multiple repositories with 3+ worktrees each.
  - Requires repeating the repository name prefix (`my-app-`) on every folder to prevent collisions with other projects.
- **Best Use Case:** Individual developers working on 1–2 primary codebases who prioritize simplicity and fast terminal navigation.
- **When NOT to Use It:** Developers juggling 10+ different repositories where parent folders quickly become unreadable.

## Strategy 2: Repository-Centric Organization

The **Repository-Centric** layout encapsulates all worktrees inside the repository's root boundary, keeping your global workspace clean.

### Filesystem Structure

```text
projects/
└── my-app/
    ├── .git/               # Administrative repository metadata
    ├── main/               # Primary working tree (main branch)
    └── worktrees/          # Dedicated container for all linked worktrees
        ├── feature-auth/   # Linked worktree -> branch: feature/auth
        ├── bugfix-login/   # Linked worktree -> branch: bugfix/login
        └── experiment/     # Linked worktree -> branch: experiment/canvas
```

### Safe Maintenance Notice

> **Important Caution on Existing Repositories:** Do not attempt to manually move your main repository's source files into a `main/` subfolder using your OS file explorer while Git is active. That breaks Git's internal relative pointers. 
> 
> If you start with a standard repository where the root folder *is* the working tree, create a `worktrees/` directory inside it and add `worktrees/` to your `.gitignore` to avoid Git treating nested worktree files as untracked parent files.

### Valid Git CLI Example

From `projects/my-app`:

```bash
# Ensure worktrees/ is ignored if nested inside the primary tree
echo "worktrees/" >> .gitignore

# Create a dedicated linked worktree inside the worktrees container
git worktree add ./worktrees/feature-auth -b feature/auth

# Create a hotfix worktree
git worktree add ./worktrees/bugfix-login -b bugfix/login main
```

### Trade-offs

- **Advantages:**
  - Self-contained: deleting or archiving `projects/my-app/` archives all associated worktrees together.
  - Keeps your top-level `projects/` directory tidy regardless of how many worktrees are spawned.
- **Disadvantages:**
  - Nested worktrees inside the primary tree require careful `.gitignore` management so the main tree does not attempt to scan sub-worktrees.
  - Some IDEs or terminal watchers attempt to recursively index child directories.
- **Best Use Case:** Developers managing dozens of different client or microservice repositories who need each repository self-contained.
- **When NOT to Use It:** Teams whose build systems or Docker volume bindings assume the repository root contains zero nested subprojects.

## Strategy 3: Branch-Type Organization

The **Branch-Type** layout groups worktrees according to your team's Git branching strategy (e.g., GitFlow or GitHub Flow).

### Filesystem Structure

```text
worktrees/
└── my-app/
    ├── features/
    │   ├── authentication/ # Linked worktree -> branch: feature/authentication
    │   └── dashboard-v2/   # Linked worktree -> branch: feature/dashboard-v2
    ├── bugfixes/
    │   └── login-error/    # Linked worktree -> branch: bugfix/login-error
    ├── hotfixes/
    │   └── prod-memory/    # Linked worktree -> branch: hotfix/prod-memory
    └── experiments/
        └── rust-core/      # Linked worktree -> branch: experiment/rust-core
```

### Valid Git CLI Example

```bash
# Create feature branch worktree
git worktree add ../worktrees/my-app/features/authentication -b feature/authentication

# Create bugfix branch worktree
git worktree add ../worktrees/my-app/bugfixes/login-error -b bugfix/login-error

# Create hotfix worktree from tag
git worktree add ../worktrees/my-app/hotfixes/prod-memory -b hotfix/prod-memory v1.2.0
```

### Trade-offs

- **Advantages:**
  - Directly mirrors Git branch naming taxonomy (`feature/*`, `bugfix/*`, `hotfix/*`).
  - Clear visual distinction between long-running features and quick production hotfixes.
  - Enables batch operations (e.g., cleaning up all directories under `experiments/`).
- **Disadvantages:**
  - Slightly deeper folder paths.
  - Empty category directories remain if not pruned when branches are deleted.
- **Best Use Case:** Structured engineering teams with disciplined branch-naming conventions (GitFlow) and multiple concurrent release tracks.
- **When NOT to Use It:** Flat branching environments where developers branch directly from `main` without type prefixes.

## Strategy 4: Ticket-Based Organization

The **Ticket-Based** structure clusters worktrees around specific Jira tickets, GitHub Issues, or Linear identifiers.

![Ticket-based Git worktree architecture showing one ticket connected to multiple implementation worktrees](/images/blog/how-to-organize-git-worktrees/ticket-based-workflow.svg)

*Organizing by issue tracker identifier allows developers to test alternative implementations side by side for a single ticket.*

### Filesystem Structure

```text
worktrees/
└── my-app/
    ├── PROJ-101/
    │   ├── implementation/ # Primary approach (OAuth2 + PKCE)
    │   └── alternative/    # Spike alternative (Session-based JWT)
    ├── PROJ-102/
    │   └── bugfix/         # Payment calculation rounding error
    └── PROJ-103/
        └── testing/        # E2E Cypress regression suite
```

### Valid Git CLI Example

```bash
# Create primary implementation for ticket PROJ-101
git worktree add ../worktrees/my-app/PROJ-101/implementation -b feat/PROJ-101-oauth

# Create an alternative spike to benchmark token payload latency
git worktree add ../worktrees/my-app/PROJ-101/alternative -b spike/PROJ-101-jwt

# Verify both worktrees point to their respective branches
git worktree list
```

### Trade-offs

- **Advantages:**
  - Instant context: you immediately know which business requirement or defect a folder belongs to.
  - Supports side-by-side architectural spikes: you can run two competing implementations of the same ticket on different ports (e.g., 3000 vs. 3001) and benchmark them without stashing.
  - Simplifies cleanup: when ticket `PROJ-101` merges, remove the entire `PROJ-101/` folder tree.
- **Disadvantages:**
  - Requires strict adherence to issue keys.
  - Non-ticketed maintenance tasks can end up without a clear home.
- **Best Use Case:** Enterprise teams working in sprint cycles with Jira, Linear, or Azure DevOps.
- **When NOT to Use It:** Open-source projects or exploratory hobby development where issues are rarely tracked formally.

## Strategy 5: AI Agent-Based Organization

With the rise of autonomous AI coding agents such as Claude Code, OpenAI Codex, Gemini CLI, Cursor Agent, and OpenCode, managing concurrent agent workspaces has become a critical developer skill.

![Multi-AI coding agent worktree isolation architecture](/images/blog/how-to-organize-git-worktrees/ai-agent-isolation.svg)

*Dedicated worktrees provide isolated working directories and independent HEAD states for each AI coding agent.*

### Filesystem Structure

```text
worktrees/
└── my-app/
    ├── human/              # Your active primary working tree
    ├── agents/
    │   ├── claude/         # Claude Code working directory -> branch: ai/claude-auth
    │   ├── codex/          # OpenAI Codex background run -> branch: ai/codex-db-opt
    │   └── gemini/         # Gemini CLI agent subagent -> branch: ai/gemini-tests
    └── review/             # Clean staging workspace to inspect & diff PRs
```

### Valid Git CLI Example

```bash
# Spin up an isolated worktree for Claude Code
git worktree add ../worktrees/my-app/agents/claude -b ai/claude-auth-refactor

# Spin up an isolated worktree for Codex to run test suites
git worktree add ../worktrees/my-app/agents/codex -b ai/codex-perf-optimization

# Spin up an isolated worktree for Gemini CLI
git worktree add ../worktrees/my-app/agents/gemini -b ai/gemini-unit-tests
```

### Critical Realities of AI Agent Worktrees

> **Security & Concurrency Warning:** 
> 1. **No Automatic Sandbox:** Git worktrees isolate filesystem files and Git staging indexes, but they do **not** provide a process sandbox or security boundary. If an agent executes `rm -rf /` or malicious bash scripts in its worktree, it impacts your host OS.
> 2. **Merge Conflicts Still Apply:** While agents operate on separate branches without disturbing your active editor, merging their outputs back into `main` will still produce Git merge conflicts if they modified overlapping code.
> 3. **Process Collisions:** If two agents attempt to execute `docker compose up` or spin up test servers, ensure their `.env` files assign unique host ports (e.g., 5001, 5002).

For a deeper dive into agentic workflows, read our dedicated guide on <a href="/blog/claude-git-worktrees" class="link-in-post">combining Claude Code with WorktreeWise</a>.

- **Best Use Case:** Agentic software engineers running multiple automated coding tools in parallel while keeping their own active editor distraction-free.
- **When NOT to Use It:** Developers who write 100% of their code manually without automated background CLI agents.

## Strategy 6: Lifecycle-Based Organization

The **Lifecycle-Based** strategy categorizes worktrees based on their expected duration and volatility.

![Lifecycle-based worktree management workflow across permanent, active, and ephemeral tiers](/images/blog/how-to-organize-git-worktrees/lifecycle-worktrees.svg)

*Categorizing worktrees into permanent, active, and ephemeral tiers eliminates sprawl and prevents accidental deletion.*

### Filesystem Structure

```text
worktrees/
└── my-app/
    ├── permanent/          # Reference trees (months to years)
    │   ├── main/           # Production baseline
    │   └── develop/        # Staging integration
    ├── active/             # Current sprint features (days to weeks)
    │   ├── feature-auth/
    │   └── bugfix-42/
    └── temporary/          # Ephemeral review & spikes (minutes to hours)
        ├── pr-review-912/
        └── spike-wasm/
```

### Lifecycle Tier Guidelines

1. **Permanent Tier:** Never deleted during routine cleanup. Lock these worktrees using `git worktree lock --reason "Production reference"` so Git will refuse to remove or prune them accidentally.
2. **Active Tier:** Daily driver workspaces where dependencies are installed and uncommitted work is actively in progress.
3. **Temporary Tier:** Disposable workspaces created for a fast PR review, diff inspection, or quick bug repro. Once closed, run `git worktree remove` without hesitation.

### Safe Removal and Prune Commands

```bash
# Lock permanent main worktree
git worktree lock ../worktrees/my-app/permanent/main --reason "Production reference"

# Safely remove a temporary review worktree once finished
git worktree remove ../worktrees/my-app/temporary/pr-review-912

# Prune stale administrative metadata
git worktree prune --verbose
```

- **Best Use Case:** Developers who frequently review colleague pull requests or conduct quick diagnostic experiments.
- **When NOT to Use It:** Small projects with only one branch active at any given moment.

## Strategy 7: Bare Repository Organization

In the **Bare Repository** layout, the central repository is cloned with the `--bare` flag. A bare repository contains *only* Git metadata (no working tree at the root level). All working code lives in explicitly linked worktrees.

### Filesystem Structure

```text
projects/
└── my-app/
    ├── .bare/              # The bare repository (stores Git objects & refs)
    ├── main/               # Linked worktree -> main branch
    ├── develop/            # Linked worktree -> develop branch
    └── feature-auth/       # Linked worktree -> feature/auth
```

### Valid Initialization Commands

```bash
# 1. Clone a bare repository into a hidden folder .bare
git clone --bare git@github.com:org/my-app.git .bare

# 2. Configure Git to fetch all remote branch heads properly
cd .bare
git config remote.origin.fetch "+refs/heads/*:refs/remotes/origin/*"

# 3. Add your primary main worktree
git worktree add ../main main

# 4. Add your feature worktree
git worktree add ../feature-auth -b feature/auth
```

### Trade-offs

- **Advantages:**
  - Perfect symmetry: `main` is treated like any other branch, rather than occupying a "special" root directory.
  - Eliminates the accidental check-in of files to the root of a non-bare repo.
  - Cleanest setup for automated CI scripts and dedicated build machines.
- **Disadvantages:**
  - Requires specific initial configuration (`remote.origin.fetch`) or `git fetch` will not track remote branches properly.
  - Confusing for Git beginners who expect a root working tree with immediate source files.
- **Best Use Case:** Advanced Git power users, DevOps engineers, and CI/CD agent runners.
- **When NOT to Use It:** Teams with onboarding developers who might be disoriented by a bare repository root.

## Strategy 8: Multi-Repository Workspace Organization

In microservice architectures, enterprise applications, or distributed full-stack stacks, a single user story often touches multiple repositories simultaneously (e.g., frontend Next.js, backend Go API, and an infrastructure Terraform repo).

The **Multi-Repository Task Workspace** groups related worktrees from *different* repositories inside one shared task directory.

### Filesystem Structure

```text
workspaces/
└── AUTH-101-OAUTH/
    ├── frontend/       # Worktree from github.com/org/web-app (feat/auth-ui)
    ├── backend/        # Worktree from github.com/org/api-service (feat/auth-api)
    └── terraform/      # Worktree from github.com/org/infra (feat/cognito)
```

### Valid Git CLI Example

```bash
# Create shared workspace directory
mkdir -p ~/workspaces/AUTH-101-OAUTH

# Link frontend worktree from web-app repository
cd ~/projects/web-app
git worktree add ~/workspaces/AUTH-101-OAUTH/frontend -b feat/auth-ui

# Link backend worktree from api-service repository
cd ~/projects/api-service
git worktree add ~/workspaces/AUTH-101-OAUTH/backend -b feat/auth-api

# Open the entire multi-repo workspace in your editor
code ~/workspaces/AUTH-101-OAUTH
```

### Distinction Notice

> **Do not confuse this with a Monorepo:** In a monorepo, a single Git repository contains multiple packages (often using tools like Turborepo or Nx). In this multi-repo strategy, you are linking worktrees from **distinct independent repositories** into a single folder so you can open them in one IDE window or run a multi-container Docker Compose environment.

- **Best Use Case:** Full-stack engineers developing coordinated microservice features across multiple Git repositories.
- **When NOT to Use It:** Monolithic single-repository codebases.

# Git Worktree Naming Conventions: How to Name Worktree Folders

A disciplined folder structure is only as effective as the names you assign to individual worktree directories.

### Why Worktree Folder Naming Matters

Unlike branch names which live strictly inside Git refs, worktree folder names live on your physical filesystem. Bad names lead to:

1. **Lost Context:** `temp2` tells you nothing about which project, branch, or ticket is inside.
2. **OS Incompatibilities:** Windows paths fail if branch names contain colons (`:`) or exceed MAX_PATH limits.
3. **Accidental Deletions:** Developers running cleanup scripts may delete active worktrees whose purpose is unclear.

### Effective vs. Ineffective Worktree Folder Names

### Guidelines for Filesystem-Safe Names

- **Sanitize Forward Slashes (`/`):** Branches often contain slashes (e.g., `feature/login`). In Unix and Windows paths, a slash represents a directory separator. Replace `/` with hyphens (`-`) or double underscores (`__`) to avoid unwanted nested subdirectories unless you explicitly want them.
- **Avoid Reserved Characters:** Do not use `:`, `*`, `?`, `"`, `<`, `>`, or `|` which are illegal on Windows filesystems.
- **Distinguish Branch Name from Folder Name:** Remember that the worktree folder name on disk does *not* have to match the branch name. You can have a worktree folder named `web-app__auth` checked out to branch `feature/jira-101-oauth-flow`.

# How to Reorganize Existing Git Worktrees Safely

What if you already have five messy worktrees scattered across your desktop and project directories?

Do **not** drag and drop worktree folders in macOS Finder or Windows Explorer! Git stores the absolute path to each linked worktree inside `.git/worktrees/<name>/gitdir`. Renaming a folder directly breaks that pointer, causing Git to throw:

```text
fatal: '<path>' is not a working tree
```

![Worktree directory health before versus after organization](/images/blog/how-to-organize-git-worktrees/before-after-organization.svg)

*Organizing existing worktrees restores predictability and eliminates orphaned Git metadata.*

### Step 1: Inspect Your Active Worktree Registry

Run `git worktree list` to see every linked worktree, its commit hash, and its checked-out branch:

```bash
git worktree list
```

For programmatic parsing in shell scripts, use the machine-readable porcelain format:

```bash
git worktree list --porcelain
```

Output:
```text
worktree /Users/developer/projects/my-app
HEAD 8f3a1b0293847291a
branch refs/heads/main

worktree /Users/developer/projects/temp-folder
HEAD 4c2e9a8b7c6d5e4f3
branch refs/heads/feature/auth
```

### Step 2: Move and Rename Folders Safely with `git worktree move`

To rename or move an existing worktree directory without corrupting Git metadata, use `git worktree move`:

```bash
# Safely move from messy path to structured path
git worktree move ../temp-folder ../worktrees/my-app/features/authentication
```

This updates both the physical folder and Git's internal pointers in `.git/worktrees/`.

> **Branch Rename vs. Worktree Move:** `git worktree move` renames the *filesystem directory*. It does not rename the Git branch. If you also want to rename the branch, navigate into that worktree and run `git branch -m <new-branch-name>`. For an end-to-end breakdown, read <a href="/blog/how-to-rename-git-worktree" class="link-in-post">How to Rename a Git Worktree</a>.

![WorktreeWise move worktree dialog](/images/v1.2.0/move-worktree.png)

*WorktreeWise provides a visual move dialog that checks path validity before moving.*

### Step 3: Repair Broken or Manually Moved Worktrees

If someone on your team *did* move a directory manually, Git provides the `repair` command to reconnect the administrative pointers:

```bash
# Run from the main repository, specifying the new path of the moved worktree
git worktree repair ../worktrees/my-app/features/authentication
```

Learn more in our interactive tutorial on <a href="/git-worktree/repair" class="link-in-post">git worktree repair</a>.

### Step 4: Safely Remove and Prune Stale Worktrees

When a feature branch is merged, clean up its working directory:

```bash
# Safely remove the worktree folder and its Git metadata
git worktree remove ../worktrees/my-app/features/authentication

# Prune administrative metadata for deleted directories
git worktree prune --verbose
```

### Precautions Before Reorganizing

- **Uncommitted Changes:** Check `git status` inside each worktree before moving or removing. If you have uncommitted changes, `git worktree remove` will refuse to delete the directory unless forced with `-f`.
- **Open IDEs and Terminals:** Close your editor or terminal session inside that directory prior to moving it to avoid file lock errors on Windows.
- **Running Dev Servers:** Stop background Node.js, Python, or Docker processes holding active handles on files in that worktree directory.
- **Locked Worktrees:** If a worktree is locked (`git worktree lock`), unlock it first using `git worktree unlock <path>`.

# Common Mistakes and Best Practices Checklist

Avoid these eight frequent pitfalls when organizing your Git worktrees:

### 1. Ambiguous Folder Names
Never name a worktree `test`, `temp`, or `final`. Use a structured naming pattern like `{repo}__{branch}` so every directory describes its purpose.

### 2. Deleting Worktree Folders Manually
Deleting a worktree folder using `rm -rf` or your OS trash bin leaves orphaned metadata inside `.git/worktrees/`. Always use `git worktree remove <path>` or run `git worktree prune` afterwards.

### 3. Checking Out an Already Checked-Out Branch
Git prohibits two worktrees from checking out the same branch simultaneously to prevent index corruption:
```text
fatal: 'feature/auth' is already checked out at '/path/to/worktree'
```
If you need to experiment on the same branch, create a new branch or worktree off that commit.

### 4. Local Port Collisions
Git worktrees isolate code files, but they share your computer's network interface. If two worktrees both attempt to run `npm run dev` on port 3000, the second will crash. Configure unique `.env.local` files with distinct ports (e.g., `PORT=3001`).

### 5. Editing `.git/worktrees` Metadata Directly
Never manually alter files inside `.git/worktrees/`. Use `git worktree move`, `git worktree lock`, and `git worktree repair` to let Git update its internal pointers safely.

### 6. Assuming Worktrees Automatically Isolate Dependencies
Worktrees share the `.git` repository, but each worktree needs its own dependencies installed (`npm install`, `pip install`, `cargo build`). While this uses more disk space, it provides complete build isolation between branches.

# Frequently Asked Questions

### Where should I store Git worktrees?
The most reliable location is in a dedicated `worktrees/` directory either inside your repository root (properly ignored in `.gitignore`) or in a sibling directory (`../worktrees/my-app/`). Avoid placing worktrees in cloud-synced folders (Dropbox, OneDrive, iCloud) because background sync daemons frequently lock Git index files.

### What is the best Git worktree folder structure?
For individual developers, the **Sibling Layout** or **Repo-Centric Layout** is best because it requires minimal overhead. For engineering teams using Jira, the **Ticket-Based Layout** (`worktrees/my-app/PROJ-101/`) is the most scalable.

### How do I name Git worktree directories?
Use a structured, filesystem-safe convention that includes both the repository name and the sanitized branch name. The WorktreeWise default preset `{repo}__wt__{branch}` (e.g., `my-app__wt__feature-login`) is ideal because it avoids path collisions across multiple repositories.

### Can I organize worktrees by feature or Jira ticket?
Yes. Grouping worktrees by ticket key (e.g., `worktrees/PROJ-101/implementation` and `worktrees/PROJ-101/alternative`) is an industry best practice. It allows you to run competing implementations side by side and cleans up easily once the ticket merges.

### Can multiple AI agents use Git worktrees simultaneously?
Yes. Giving each AI coding agent (such as Claude Code, OpenAI Codex, or Gemini CLI) its own dedicated worktree allows agents to edit files, run test suites, and execute builds in parallel without overwriting your active editor. However, worktrees do not provide security sandboxing or eliminate merge conflicts when merging to `main`.

### Can I move an existing Git worktree safely?
Yes, but always use `git worktree move <source> <destination>` rather than your operating system's file manager. If a directory was moved manually, run `git worktree repair <new-path>` from the main repository to reconnect Git's internal pointers.

### Does Git automatically delete unused worktrees?
No. Git does not delete physical worktree folders automatically. If you delete a folder manually, running `git worktree prune` cleans up Git's internal administrative references, but you should always use `git worktree remove <path>` to delete worktrees cleanly.

WorktreeWise automatically sanitizes illegal characters and generates predictable folder paths every time you create a worktree.
